# Candidate Volunteer Sprints / Project Pods

These are intentionally small, outcome-based technical or research projects that could be suitable for short volunteer sprints, including future GitHub for Nonprofits Project Pods.

They are **candidates**, not commitments. Scope should be validated before recruitment.

## 1. 5 Practice Accessibility Sprint

**Goal:** produce and implement a prioritized accessibility improvement pass for the public 5 Practice experience.

**Potential team:** accessibility specialist, frontend developer, QA tester.

**Possible outputs:**
- WCAG-oriented audit;
- keyboard and screen-reader fixes;
- reduced-motion review;
- mobile touch-target fixes;
- accessibility regression checklist.

**Good scope:** 1–2 weeks.

## 2. Atlas of Peace — Data Prototype

**Goal:** build a small, inspectable prototype that demonstrates how peace-related datasets and institutions could be represented.

**Potential team:** data engineer, researcher, frontend/data-visualization developer.

**Possible outputs:**
- source inventory;
- minimal data schema;
- provenance fields;
- one prototype visualization or searchable table;
- documentation of limitations and bias risks.

**Good scope:** 2–4 weeks.

## 3. True Cost of War — Visualization & Accessibility Review

**Goal:** improve how a public-interest data tool communicates difficult evidence clearly and accessibly.

**Potential team:** data-visualization designer, frontend developer, accessibility reviewer, researcher.

**Possible outputs:**
- visual hierarchy review;
- chart/table accessibility recommendations;
- source/provenance UX improvements;
- mobile and assistive-technology QA;
- reusable visualization guidelines.

**Good scope:** 1–3 weeks.

## 4. Multilingual Publishing QA Toolkit

**Goal:** create a lightweight, reusable process for checking multilingual Peaceful World content before publication.

**Potential team:** localization engineer, editor, developer, multilingual reviewers.

**Possible outputs:**
- terminology consistency checks;
- missing-string detection;
- layout-overflow checks;
- reviewer checklist;
- documentation for adding a new language.

**Good scope:** 1–2 weeks.

## Principles for volunteer sprints

A sprint should:

- have one clear outcome;
- avoid requiring access to sensitive information;
- be small enough to finish;
- have a named internal reviewer;
- leave behind documentation;
- produce something reusable or directly useful to users;
- avoid creating a maintenance burden larger than the value delivered.

If you are interested in one of these areas, see [VOLUNTEER.md](VOLUNTEER.md) or open a volunteer contribution proposal.
