# Peaceful World — Public Roadmap

This is a living, intentionally high-level view of what Peaceful World is building. It is not a promise of exact delivery dates. Priorities can change as research, resources and user feedback change.

## Now

### 5 Practice
- harden the web and mobile experience;
- improve localization and accessibility;
- make analytics useful without turning the practice into a surveillance product;
- complete Android release work;
- keep iOS infrastructure ready while Apple development is paused.

### Peaceful World website and infrastructure
- move selected public-facing components to GitHub-backed infrastructure;
- improve maintainability, performance and transparency;
- build a public GitHub layer that shows how the organization works without exposing private development repositories.

### Peace literacy research and publishing
- publish research-backed long-form work;
- connect research to practical educational tools;
- expand multilingual access.

### Open collaboration
- create clear public contribution paths;
- publish small, well-scoped volunteer tasks;
- prepare suitable projects for nonprofit technical volunteering programs.

## Next

### 42 Lessons
- finalize editorial structure;
- prepare multilingual publication workflows;
- connect lessons to practical exercises and supporting research.

### Atlas of Peace
- define the information architecture;
- identify useful datasets, institutions and public resources;
- prototype contribution and review workflows.

### Public-interest data tools
- refine how projects such as True Cost of War present complex evidence;
- improve source transparency and data visualization;
- identify reusable public components.

## Later / exploratory

- open datasets and APIs where they create real public value;
- reusable tools for peace education organizations;
- additional language infrastructure;
- contributor-led experiments that fit Peaceful World's mission and ethics.

## How to help

See [VOLUNTEER.md](VOLUNTEER.md). We especially value contributions that are small enough to finish, easy to review, and clearly useful to real users.

## How this roadmap is maintained

Items should move because the underlying work changed, not because a calendar says they should. Completed work should eventually be reflected in public releases, changelogs or project updates where appropriate.
